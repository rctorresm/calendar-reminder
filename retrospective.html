Build Retrospective

Calendar Reminder

A Windows desktop app that watches a virtual assistant's shared Google Calendars and won't let a reminder go unnoticed — built session-long, end to end, and now running on a second person's PC.

Foundation

Python + PySide6, built to spec: OAuth sign-in (read-only Calendar scope only), a two-loop scheduler — sync the calendar list and events, then check what's due — SQLite cache, Windows toast notifications, system tray, and start-with-Windows. Shipped with 21 tests before a single manual click.

  • Security was the design brief, not an afterthought: no auto-update mechanism anywhere in the app (the single biggest way a legitimate tool turns into a backdoor later), refresh token in Windows Credential Manager via keyring — never a plaintext file, parameterized SQL throughout, a single-instance guard so two copies can never both decide "not yet notified" for the same event.
  • The distribution model was a deliberate trade-off, made explicitly: one shared Google Cloud OAuth client baked into every build, so a recipient never touches Google Cloud Console — traded against the isolation of everyone bringing their own client. Documented candidly in SECURITY.md, with a per-install opt-out left in Settings for anyone who wants it.

Getting the credentials in place

The one step that couldn't be automated: signing into a real Google account and clicking through Google's own consent screens. Walked through it live, screen by screen — new Cloud project, Calendar API enabled, OAuth consent screen configured External, calendar.readonly scope added, a Desktop OAuth client created, and the resulting client_secret.json downloaded and placed. Confirmed along the way that Testing-mode apps cap out at 100 pre-approved emails and log test users out every 7 days — the real reason a colleague's corporate sign-in needed her email added to that list by hand later on.

Living with it — the reminder itself evolved from watching it fire

Every change here came from actually using the app, not from re-reading the spec.

  • The attention cue, three iterations: a fixed few flashes of the screen border → not persistent enough for someone turned away from their desk, so it became an indefinite breathing pulse paired with a details window that only stops when acknowledged. The border itself went from a blink to an eased fade, 3× slower on request, then user-adjustable (Slow / Normal / Fast).
  • One color for everyone became one color per calendar — first as a dropdown, then rebuilt as an actual clickable swatch after "I don't want the color's name, I want to see the color," and expanded from 6 to 9 (three more — pink, teal, brown — added on request). The same color now tints its calendar's row in the Upcoming Events table, so whose event it is reads at a glance.
  • Sync went from a 5-minute rolling window to once a minute, aligned to the wall clock (:00 and :30), after noticing the two loops didn't line up — which surfaced a real race condition (below).
  • "Just today" turned out to need its own fix — the sync window was a rolling 24 hours from right now, which quietly bled into tomorrow rather than stopping at midnight.

Making it feel like real software

  • Switching Google accounts used to silently delete the previous account's calendars — colors included — since nothing tracked which account a calendar belonged to. Fixed by scoping every calendar row to its account (identified via that account's own primary-calendar ID, no extra permission needed), verified against the live database with real calendars, not just a synthetic test.
  • A custom icon, redesigned once on feedback: from a blue "R" badge to a white-ground calendar glyph with an orange warning triangle — checked for legibility at actual 16px tray size before finalizing either time.
  • Confirmed the close button was already wired to minimize to tray rather than quit, with "Quit" reserved for the tray's own menu.

Turning it into a file a second person could run

Packaging surfaced two bugs that never would have shown up running from source — the kind that only exist once code is actually frozen into an .exe.

Real bugs, found and fixed

01 Sync and reminder check could run in either order

Two scheduled jobs due at the exact same instant have no guaranteed order — the reminder check could run before that minute's sync finished, seeing stale data and deferring a fresh event to the next tick.

Fix: one function call — sync, then check — instead of two independent jobs hoping to land in sequence.

02 Sound toggle could never actually turn sound on

The toast library defaults every notification to silent unless told otherwise. The code only ever called that setting to turn sound off — never to turn it on — so the checkbox had no real effect either way.

Fix: switched to winsound.MessageBeep, a direct Windows call that doesn't depend on the toast's own audio path (which separately turned out to need a registered app shortcut this app doesn't have).

03 The database schema went missing in the packaged build

The schema lived in its own .sql file — invisible to PyInstaller's automatic bundling, which only follows Python imports. The packaged app crashed on first launch with a file-not-found.

Fix: embedded the schema as a Python string in db.py instead of documenting one more easy-to-forget build flag — removes the failure mode rather than papering over it.

04 Bundled files were being looked for in the wrong folder

Modern PyInstaller puts bundled data in an _internal\ subfolder next to the .exe, not the exe's own folder — the app was resolving client_secret.json and the icon to a path that doesn't exist in a real packaged build.

Fix: resolve via sys._MEIPASS, the path PyInstaller's own bootloader sets for exactly this — with a regression test locking in which one wins.

05 "Today's events" was a rolling 24 hours, not a calendar day

The sync window ran from right now to 24 hours later — technically not "forever," since every sync fully replaces the cache, but it did bleed past midnight into tomorrow.

Fix: bounded to local midnight instead, for both the sync window and the Upcoming Events display.

06 Switching Google accounts deleted the other account's calendars

The cleanup step that drops calendars no longer visible to the signed-in account wasn't scoped to that account — so switching accounts wiped every calendar (and its chosen color) that didn't belong to the new one.

Fix: every calendar row is tagged with the account it came from; switching away just hides it, switching back brings it — and its color — right back.

Left for later, on purpose

  • Feature Bring back the "Copy Reminder" button on the alert window, removed earlier when the window was simplified.
  • Process Move the Google Cloud OAuth app from Testing to a verified Production app, so sign-in isn't limited to a pre-approved email list and sessions stop expiring every 7 days.
  • Accepted If the exact same calendar were ever shared to two different Google accounts used on one machine, only one account's copy would be tracked — a known, accepted limitation for how this app is actually used.
